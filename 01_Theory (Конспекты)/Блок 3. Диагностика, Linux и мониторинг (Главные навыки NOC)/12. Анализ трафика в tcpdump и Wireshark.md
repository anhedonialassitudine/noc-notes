# 12. Анализ трафика в tcpdump и Wireshark

Теги: #cli #troubleshooting #network #tcpdump #wireshark #tshark #pcap #span #base

## Суть простыми словами
**Анализаторы трафика (снифферы)** позволяют заглянуть внутрь сетевых пакетов, проходящих через сетевую карту, в реальном времени (уровни [[01. Модели OSI и TCP-IP|L2–L7]]).

* **`tcpdump`:** Консольная утилита для Linux. Используется непосредственно на серверах и роутерах без графического интерфейса для быстрой проверки прохождения пакетов и записи дампов в файл (`.pcap`).
* **`Wireshark`:** Мощная графическая программа для ПК. Используется для глубокого анализа сложных дампов, поиска ретрансмиссий, проблем с SSL/TLS и разбора протоколов.
* **`tshark`:** Консольная версия Wireshark для Linux. Позволяет анализировать сложные `.pcap` файлы и извлекать поля протоколов прямо в терминале сервера без скачивания дампа на ПК.

> **Золотое правило связки:** Захватываем трафик на сервере в файл через `tcpdump -w dump.pcap`, скачиваем файл на свой компьютер (через `scp` или SFTP) и удобно анализируем в `Wireshark`.

## 1. Утилита `tcpdump`: главные ключи и фильтры (BPF)
Для фильтров захвата `tcpdump` использует синтаксис **BPF (Berkeley Packet Filter)**.

### Обязательные флаги (Запомнить наизусть!)
* **`-i <интерфейс>`:** На каком интерфейсе слушать трафик (`-i eth0` или `-i any` для всех сразу).
* **`-nn`:** **НИКОГДА не резолвить** IP-адреса в домены и номера портов в названия (ускоряет работу в 10 раз и не забивает канал лишними DNS-запросами!).
* **`-v` / `-vv`:** Подробный вывод (показывает TTL, IP ID, длину пакета, флаги TCP).
* **`-c <число>`:** Остановиться автоматически после захвата N пакетов (чтобы случайно не забить весь диск на сервере!).
* **`-w <файл.pcap>`:** Записать сырые пакеты в файл для Wireshark (вместо вывода на экран).
* **`-r <файл.pcap>`:** Прочитать ранее записанный файл дампа в консоли.

### Готовые боевые однострочники `tcpdump`
```bash
# 1. Перехватить весь трафик до/от конкретного IP-адреса (остановиться через 100 пакетов)
sudo tcpdump -i any -nn -c 100 host 10.10.1.50

# 2. Проверить, прилетают ли пинги (ICMP) на сервер
sudo tcpdump -i eth0 -nn icmp

# 3. Отловить только попытки установки TCP-соединения (флаг SYN) на 443 порт
sudo tcpdump -i eth0 -nn 'tcp port 443 and (tcp[tcpflags] & tcp-syn != 0)'

# 4. Слушать DNS-запросы и ответы (UDP/TCP порт 53)
sudo tcpdump -i any -nn port 53

# 5. Записать трафик конкретного хоста и порта в файл (с полным размером пакета -s 0)
sudo tcpdump -i eth0 -nn -s 0 host 192.168.1.10 and port 8080 -w /tmp/debug.pcap

# 6. Логические операторы: исключить свой же SSH-трафик (порт 22), чтобы не засорять экран!
sudo tcpdump -i eth0 -nn not port 22

# 7. Кольцевой буфер (Ring Buffer) для отлова плавающих аварий: писать по кругу 5 файлов по 100 МБ (-C 100 -W 5), чтобы не забить диск!
sudo tcpdump -i eth0 -nn -C 100 -W 5 -w /tmp/ring_capture.pcap
```

## 2. Как читать вывод `tcpdump` в консоли
Типичная строчка из вывода `tcpdump -nn`:
`14:22:01.123456 IP 192.168.1.10.54321 > 10.0.0.5.443: Flags [S], seq 1000, win 64240, options [mss 1460], length 0`

* `14:22:01.123456` — точное время получения пакета.
* `192.168.1.10.54321 > 10.0.0.5.443` — отправитель (порт `54321`) -> получатель (порт `443`).
* `Flags [S]` — TCP-флаги:
  * **`[S]`** = `SYN` (запрос соединения)
  * **`[S.]`** = `SYN-ACK` (подтверждение сервера)
  * **`[.]`** = `ACK` (подтверждение)
  * **`[P.]`** = `PSH-ACK` (передача реальных данных)
  * **`[F.]`** = `FIN-ACK` (штатное закрытие сессии)
  * **`[R]`** или **`[R.]`** = `RST` (аварийный сброс соединения!)
* `length 0` — размер полезных данных в байтах (в рукопожатии данных еще нет, поэтому `0`).

## 3. Программа Wireshark и консольный `tshark`: фильтры отображения (Display Filters)
В Wireshark синтаксис фильтров отличается от `tcpdump` (используется `==`, `&&`, `||`).

| Задача в Wireshark | Фильтр отображения (Display Filter) |
| :--- | :--- |
| **Весь трафик конкретного IP** | `ip.addr == 192.168.1.10` |
| **Трафик строго ОТ или К IP** | `ip.src == 192.168.1.10` / `ip.dst == 10.0.0.5` |
| **Фильтр по порту TCP или UDP** | `tcp.port == 443` / `udp.port == 53` |
| **Только DNS- или HTTP-трафик** | `dns` / `http` |
| **Найти все сбросы соединений (RST)** | `tcp.flags.reset == 1` |
| **Найти только начало сессий (SYN)** | `tcp.flags.syn == 1 && tcp.flags.ack == 0` |
| **Найти потери и ретрансмиссии (проблемы канала!)** | `tcp.analysis.retransmission` или `tcp.analysis.flags` |
| **Найти ошибки DNS (NXDOMAIN, SERVFAIL)** | `dns.flags.rcode != 0` |
| **Найти все HTTPS-запросы к конкретному домену (по SNI)** | `tls.handshake.extensions_server_name == "example.com"` |

### Главные приемы в Wireshark и `tshark`
* **Follow -> TCP Stream (Правый клик по пакету):** Собирает все разрозненные пакеты одной сессии в единый читаемый диалог (красный текст — запрос клиента, синий — ответ сервера). Незаменимо для анализа незашифрованного HTTP, SMTP, FTP или SQL.
* **Statistics -> Conversations / Endpoints:** Показывает, какие два IP-адреса генерируют больше всего трафика (помогает за секунду найти источник DDoS или торрент в офисной сети).
* **Expert Information (Analyze -> Expert Information):** Автоматически подсвечивает красным и желтым все аномалии в дампе (потери пакетов, дубликаты ACK, нулевое окно `TCP ZeroWindow`, ошибки контрольных сумм).
* **Быстрый разбор дампа на сервере через `tshark`:**
  ```bash
  # Вытащить из дампа только ретрансмиссии TCP без открытия графического интерфейса
  tshark -r /tmp/debug.pcap -Y "tcp.analysis.retransmission"
  ```

## 4. Захват трафика на коммутаторах и маршрутизаторах (SPAN / Mirroring)
Когда проблема возникает на IP-телефоне, камере или закрытом оборудовании, куда нельзя зайти по SSH и запустить `tcpdump`, трафик снимают средствами сети:
* **SPAN (Switched Port Analyzer / Port Mirroring):** Функция на управляемом коммутаторе L2/L3, которая копирует весь трафик с проблемного порта (Source Port) на порт (Destination Port), куда подключен ноутбук инженера с запущенным Wireshark.
* **RSPAN / ERSPAN:** Удаленное зеркалирование трафика через специальный VLAN (RSPAN) или поверх IP-туннеля GRE (ERSPAN), чтобы отправить копию пакетов в центральный дата-центр инженеру NOC.

## Практика NOC: 4 типовых сценария при анализе дампа
1. **Видим только `Flags [S]` (SYN), и они повторяются через 1, 2, 4 секунды, а ответа нет:** Пакеты до сервера не доходят (блокирует промежуточный файрвол, неверный маршрут) либо сам сервер отбрасывает их локальным `iptables DROP`.
2. **Видим `Flags [S]`, а в ответ сразу прилетает `Flags [R.]` (RST-ACK):** Сеть работает идеально, пакет дошел до сервера, но на сервере **закрыт порт** (упал Nginx/база данных или слушает другой порт).
3. **Рукопожатие прошло (`[S]`, `[S.]`, `[.]`), клиент отправил `Client Hello` (TLS), и связь зависла:** Классическая проблема с **[[01. Модели OSI и TCP-IP|MTU]]**! Маленькие пакеты рукопожатия прошли, а большой пакет с сертификатом (1500 байт) застрял в VPN-туннеле.
4. **В Wireshark много черных строк `TCP Retransmission` и `TCP Dup ACK`:** На линии теряются пакеты (битый патч-корд, перегрузка канала у провайдера или ошибки на оптике).

## Частые вопросы на собеседовании
* **Почему при запуске `tcpdump` всегда нужно добавлять ключ `-nn`?** Без `-nn` утилита пытается для каждого перехваченного IP-адреса сделать обратный DNS-запрос (PTR), что вызывает огромные задержки вывода и генерирует паразитный DNS-трафик в дампе.
* **Можно ли в Wireshark прочитать зашифрованный HTTPS (TLS) трафик?** Содержимое (тело запроса и пароли) без секретных ключей сессии (`SSLKEYLOGFILE`) прочитать нельзя, но **метаданные** видны всегда: IP-адреса, порты, время задержек, ретрансмиссии, версия TLS и имя домена в открытом поле **SNI (Server Name Indication)** внутри пакета `Client Hello`.
* **Как в `tcpdump` перехватить трафик с тегами VLAN (802.1Q)?** Добавить флаг `-e` (показывает заголовки канального уровня L2, включая MAC-адреса и номер VLAN ID) и фильтр `vlan`.
