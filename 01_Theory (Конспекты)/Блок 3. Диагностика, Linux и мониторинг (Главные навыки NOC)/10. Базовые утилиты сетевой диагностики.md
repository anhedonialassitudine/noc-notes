# 10. Базовые утилиты сетевой диагностики (ping, traceroute, mtr, curl, openssl)

Теги: #cli #troubleshooting #network #ping #traceroute #mtr #curl #openssl #icmp #base

## Суть простыми словами
**Утилиты диагностики** — это ежедневный рабочий инструмент NOC-инженера. Когда приходит алерт «сервер недоступен» или «сайт тормозит», именно эти команды позволяют за пару минут определить, на каком уровне ([[01. Модели OSI и TCP-IP|L3, L4 или L7]]) и на чьей стороне (ваш сервер, ваш роутер, аплинк-провайдер или конечный ресурс) произошел сбой.

## 1. Утилита `ping` (Проверка доступности на L3)
Работает поверх протокола **ICMP** (отправляет `Echo Request` Type 8 и ждет `Echo Reply` Type 0).

### Что мы смотрим в выводе `ping`
* **`time` (RTT — Round-Trip Time):** Время в миллисекундах (`ms`), за которое пакет дошел до цели и вернулся обратно. Резкие скачки RTT (например, с `10 ms` до `450 ms`) говорят о перегрузке канала (**Jitter / джиттер**).
* **`ttl` (Time To Live):** Оставшееся количество прыжков (роутеров). По стартовому значению TTL можно косвенно определить ОС удаленного узла:
  * **Linux / macOS / сетевое оборудование:** стартовый TTL обычно **`64`** (пришло `57` -> пакет прошел 7 роутеров).
  * **Windows:** стартовый TTL обычно **`128`** (пришло `119` -> пакет прошел 9 роутеров).
  * **Cisco IOS:** стартовый TTL часто **`255`**.
* **`packet loss` (% потерь):** В норме должно быть **`0%`**. Даже `1–3%` потерь уже критичны для IP-телефонии (VoIP), видеозвонков и онлайн-игр.

### Полезные ключи `ping` (Linux / Windows)
```bash
# Отправить 10 пакетов с интервалом 0.2 сек (быстрый тест потерь в Linux)
ping -c 10 -i 0.2 8.8.8.8

# Указать конкретный исходящий интерфейс или IP (проверка канала конкретного провайдера)
ping -I eth1 8.8.8.8

# Проверка реального MTU канала (запрет фрагментации + размер 1472 байта = 1500 IP)
ping -M do -s 1472 192.168.1.1      # Linux
ping -f -l 1472 192.168.1.1         # Windows
```

## 2. Утилиты `traceroute` и `mtr` (Поиск проблемного узла на маршруте)
Показывают весь путь пакета от вашего устройства до цели через каждый промежуточный маршрутизатор (хоп — *hop*).

### Как это работает под капотом
Утилита отправляет пакеты с искусственно заниженным **TTL**: первый пакет с `TTL=1` (первый роутер сбрасывает его до 0 и возвращает `ICMP Time Exceeded` — так мы узнаем его IP), второй с `TTL=2` и так далее до самой цели.
* **Linux (`traceroute`):** По умолчанию использует **UDP-пакеты** (порты `33434+`).
* **Windows (`tracert`):** По умолчанию использует **ICMP Echo Request**.

### Почему `mtr` (My Traceroute) лучше обычного `traceroute`
`mtr` объединяет `ping` и `traceroute` в реальном времени, постоянно отправляя серии пакетов и считая статистику потерь и задержек для каждого узла.
```bash
# Запустить отчет MTR на 50 пакетов без резолва DNS (самый быстрый и наглядный формат для тикета провайдеру)
mtr -r -n -c 50 1.1.1.1

# Запустить MTR в режиме TCP (полезно, если провайдер режет ICMP/UDP)
mtr -r -n -T -P 443 -c 30 google.com

# Показать номера автономных систем (ASN) каждого узла на маршруте (удобно искать, чей это роутер)
mtr -r -n -z -c 30 8.8.8.8
```

### Главные правила NOC при чтении `mtr`
* **Потери `50%` на одном промежуточном хопе (например, хоп № 4), но на конечном хопе (хоп № 10) потерь `0%`:** **ЭТО НЕ АВАРИЯ!** Магистральные маршрутизаторы провайдеров защищают свой процессор (Control Plane Policing) и искусственно ограничивают скорость ответов на ICMP-пакеты, адресованные им лично, но транзитный трафик пропускают на 100%.
* **Потери `30%` начались на хопе № 4 и сохраняются на всех последующих хопах (№ 5, 6, 7... до конца):** **ЭТО РЕАЛЬНАЯ АВАРИЯ** на стыке между 3-м и 4-м узлом или перегрузка 4-го узла. Именно этот отчет прикладывают в тикет провайдеру.
* **Звездочки `* * *` на одном из хопов:** Узел настроен не отвечать на ICMP/UDP-зонды (файрвол), но трафик через него проходит нормально, если дальше маршрут продолжается.
* **Правило двухсторонней диагностики (Looking Glass):** Прямой `mtr` показывает только путь **туда** (`A -> B`). Из-за асимметричной маршрутизации в интернете пакеты обратно (`B -> A`) могут идти через другого оператора, где и теряются. Всегда запрашивайте **обратный `mtr`** со стороны удаленного узла или проверяйте маршрут через публичные **Looking Glass (LG)** серверы провайдеров.

## 3. Утилиты `curl` и `openssl` (Проверка веб-сервисов и SSL на L7)
Позволяют проверить работу HTTP/HTTPS-серверов, SSL-сертификатов, редиректов и API прямо из консоли без браузера.

### Полезные команды `curl` для NOC
```bash
# Получить только HTTP-заголовки ответа (быстрая проверка, жив ли сайт и какой код отдает)
curl -I https://example.com

# Проследить всю цепочку редиректов (301 -> 302 -> 200) до конечной страницы
curl -IL https://example.com

# Проигнорировать ошибку самоподписанного SSL-сертификата (для внутренних панелей управления)
curl -Ik https://192.168.1.1:8443

# Максимально подробный вывод (DNS, TCP-рукопожатие, TLS/SSL-сертификат, заголовки)
curl -v https://example.com

# Замерить точное время каждого этапа загрузки (DNS, Connect, TLS, TTFB, Total)
curl -o /dev/null -s -w "DNS: %{time_namelookup}s | Connect: %{time_connect}s | TLS: %{time_appconnect}s | TTFB: %{time_starttransfer}s | Total: %{time_total}s\n" https://example.com

# Проверить работу сайта на конкретном бэкенд-сервере (в обход DNS и балансировщика)
curl -I --resolve example.com:443:10.10.1.50 https://example.com
```

### Проверка срока действия SSL/TLS-сертификата через `openssl`
Очень частая причина инцидентов в NOC — забыли продлить SSL-сертификат на сайте или API:
```bash
# Посмотреть даты выпуска и окончания действия SSL-сертификата (поддержка SNI через -servername)
echo | openssl s_client -servername example.com -connect example.com:443 2>/dev/null | openssl x509 -noout -dates
```

### Главные коды ответов HTTP, которые нужно знать в NOC
* **`200 OK`:** Всё работает штатно.
* **`301 / 302`:** Редирект (перенаправление, например с HTTP на HTTPS).
* **`401 / 403`:** Ошибка авторизации или доступ запрещен (сервер работает, но не пускает).
* **`404 Not Found`:** Страница не найдена (веб-сервер жив, проблема в пути или приложении).
* **`500 Internal Server Error`:** Внутренняя ошибка приложения/кода на сервере.
* **`502 Bad Gateway`:** Прокси-сервер (например, Nginx) жив, но бэкенд-приложение за ним упало или не отвечает.
* **`503 Service Unavailable`:** Сервер перегружен или на техобслуживании.
* **`504 Gateway Timeout`:** Бэкенд-сервер слишком долго обрабатывает запрос, и прокси сбросил ожидание по таймауту.

## Практика NOC: пошаговый алгоритм проверки «Сайт не открывается»
1. `ping 8.8.8.8` — проверяем, есть ли вообще выход в интернет (L3).
2. `dig example.com +short` — проверяем, резолвится ли домен в IP (L7 DNS).
3. `mtr -r -n -c 20 example.com` — смотрим, доходят ли пакеты до сервера и нет ли потерь у провайдера (L3).
4. `nc -zv example.com 443` — проверяем, открыт ли TCP-порт 443 (L4).
5. `curl -Iv https://example.com` — смотрим код ответа HTTP и валидность SSL-сертификата (L7).

## Частые вопросы на собеседовании
* **Если `ping` до сервера не проходит, значит ли это, что сервер «лежит»?** Нет. Администратор мог заблокировать входящий протокол **ICMP** на файрволе. Всегда проверяйте доступность целевого порта приложения (например, `nc -zv IP 443` или `curl`).
* **В чем разница между `traceroute` в Linux и `tracert` в Windows?** В Linux по умолчанию отправляются **UDP-пакеты** на высокие порты (чтобы конечный узел вернул `ICMP Port Unreachable`), а в Windows — **ICMP Echo Request**. Из-за этого один и тот же маршрут может по-разному проходить через строгие файрволы.
* **Что такое TTFB (Time To First Byte) в выводе `curl`?** Время от отправки HTTP-запроса до получения первого байта ответа от сервера. Высокий TTFB при низком `ping` означает, что сеть в порядке, а тормозит сам сервер (база данных, PHP/Python-код или нехватка CPU/RAM).
