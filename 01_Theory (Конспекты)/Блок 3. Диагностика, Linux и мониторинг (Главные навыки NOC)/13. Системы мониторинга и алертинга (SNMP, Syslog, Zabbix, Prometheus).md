# 13. Системы мониторинга и алертинга (SNMP, Syslog, Zabbix, Prometheus)

Теги: #theory #monitoring #noc #snmp #syslog #netflow #zabbix #prometheus #grafana #base

## Суть простыми словами
**Мониторинг** — это «глаза и уши» инженера NOC. Вместо того чтобы вручную проверять сотни серверов и коммутаторов, системы мониторинга непрерывно собирают метрики (загрузку CPU, память, температуру, трафик на портах, статус BGP-сессий) и логи, строят графики и отправляют **алерты (уведомления)** при выходе показателей за норму.

В основе сбора данных лежат две модели:
* **Pull-модель (Опрос):** Сервер мониторинга сам регулярно «стучится» на устройство или агент и забирает метрики (классика для SNMP и Prometheus).
* **Push-модель (Отправка):** Само устройство или установленный на нем агент активно отправляет данные или сообщения об авариях на сервер мониторинга (SNMP Trap, Syslog, Zabbix Active Agent, NetFlow).

## 1. Протокол SNMP (Simple Network Management Protocol)
Главный стандарт мониторинга сетевого оборудования (коммутаторов, маршрутизаторов, ИБП, принтеров). Работает на прикладном уровне ([[01. Модели OSI и TCP-IP|L7]]) поверх **UDP**:
* **Порт `UDP 161`:** Сервер мониторинга (Manager) опрашивает устройство (Agent) командами `GET` / `GETNEXT` / `GETBULK`.
* **Порт `UDP 162`:** Само устройство экстренно отправляет сообщение об аварии (**SNMP Trap**) на сервер мониторинга без ожидания планового опроса (например, при падении физического порта или блока питания).

### Ключевые понятия SNMP
* **MIB (Management Information Base):** Иерархическая база данных (справочник), описывающая, какие именно параметры умеет отдавать устройство.
* **OID (Object Identifier):** Уникальный числовой адрес конкретной метрики в дереве MIB (например, `1.3.6.1.2.1.1.3.0` — время работы устройства `sysUpTime`).
* **Версии SNMP (Важно для собеседования!):**
  * **SNMPv1 / SNMPv2c:** Авторизация происходит по простому текстовому паролю — **Community String** (по умолчанию `public` для чтения и `private` для записи). Весь трафик идет **в открытом виде без шифрования**.
  * **SNMPv3:** Современный безопасный стандарт. Поддерживает аутентификацию по логину/паролю (`auth`) и полное шифрование трафика (`priv` — AES/DES).

## 2. Протокол Syslog (Сбор системных логов)
**Syslog** — стандарт централизованной отправки текстовых журналов событий с маршрутизаторов, коммутаторов и Linux-серверов на единый лог-сервер (Graylog, ELK Stack, Grafana Loki). Работает по **UDP 514** (или **TCP 514 / TLS 6514** для надежной доставки).

> **Критически важное правило NOC:** Чтобы правильно сопоставить логи с разных устройств во время расследования аварии, на всех серверах и роутерах должно быть настроено единое точное время по протоколу **[[05. Протоколы TCP и UDP|NTP (UDP 123)]]**!

### 8 уровней критичности Syslog (Severity Levels — от 0 до 7)
Чем **меньше** цифра, тем страшнее авария:

| Код | Название | Описание | Реакция NOC |
| :--- | :--- | :--- | :--- |
| **0** | **Emergency (`emerg`)** | Система полностью неработоспособна | Немедленная эскалация P1 (Critical) |
| **1** | **Alert (`alert`)** | Требуется немедленное вмешательство (например, отказ БД или ядра) | Немедленная реакция |
| **2** | **Critical (`crit`)** | Критические ошибки (отказ блока питания, перегрев, переполнение диска) | Высокий приоритет |
| **3** | **Error (`err`)** | Ошибки в работе сервисов или интерфейсов | Требует проверки и тикета |
| **4** | **Warning (`warn`)** | Предупреждения (скоро закончится место, высокая загрузка CPU) | Взять на контроль |
| **5** | **Notice (`notice`)** | Важные штатные события (например, интерфейс перешел в `UP/DOWN`) | Информационно |
| **6** | **Informational (`info`)** | Обычные информационные сообщения | Для истории / аудита |
| **7** | **Debug (`debug`)** | Отладочная информация для разработчиков и инженеров | Включается только при диагностике |

## 3. Анализ трафика и внешний контроль: NetFlow и Synthetic Monitoring
* **NetFlow / sFlow / IPFIX (Анализ потоков трафика):** SNMP показывает только общую загрузку интерфейса (например, `980 Мбит/с`), но не говорит, **кто** создает эту нагрузку. Протоколы NetFlow (Cisco), sFlow и IPFIX отправляют на коллектор статистику сессий (Source IP, Destination IP, порты, протокол и объем байт), позволяя NOC мгновенно обнаружить DDoS-атаку или найти хост, забивший канал.
* **Whitebox vs Blackbox (Синтетический мониторинг):**
  * *Whitebox* — мониторинг сервера изнутри (CPU, память, диски).
  * *Blackbox (Синтетический мониторинг)* — проверка сервиса снаружи глазами пользователя (например, **Prometheus Blackbox Exporter** каждые 15 секунд проверяет код ответа HTTPS, время ответа DNS и срок истечения SSL-сертификата с разных географических точек).

## 4. Сравнение популярных систем мониторинга: Zabbix vs Prometheus + Grafana

| Характеристика | Zabbix | Prometheus + Grafana |
| :--- | :--- | :--- |
| **Основная специализация** | Универсальный мониторинг серверов, **сетевого оборудования (SNMP)** и ИБП | Мониторинг микросервисов, контейнеров (Docker/Kubernetes), облаков и приложений |
| **Как собирает данные** | Агенты (Push/Pull), **SNMP**, ICMP, IPMI, JMX | В основном **Pull-модель** (сам ходит по HTTP `/metrics` на специальные программы — **Exporters**) |
| **Хранение данных** | Классические реляционные БД (PostgreSQL, MySQL) | Встроенная база временных рядов (**TSDB — Time Series Database**) |
| **Визуализация** | Встроенные графики и карты сети (часто подключают Grafana) | **Grafana** (золотой стандарт красивых интерактивных дашбордов) |
| **Язык запросов** | Триггеры и выражения Zabbix | **PromQL** (мощный язык запросов для агрегации метрик) |

## Практика NOC: диагностика и работа с алертами
* **Что такое Alert Fatigue (Усталость от алертов) и Flapping (Дребезг):** Если настроить алерт на скачок CPU > 80% на 1 секунду, чат дежурных завалит сотнями ложных срабатываний. Чтобы этого избежать, используют:
  * **Гистерезис:** Срабатывание при > 90% в течение 5 минут, а закрытие — только когда упадет ниже 75%.
  * **Зависимости (Dependencies):** Если упал главный роутер офиса, система должна прислать **1 алерт** о падении роутера, а не 50 алертов о недоступности каждого компьютера за ним.
  * **Режим обслуживания (Maintenance Window / Silence):** Обязательное отключение уведомлений по узлу на время плановых ночных работ.
* **Полезные команды для проверки SNMP в Linux (`net-snmp-utils`):**
  ```bash
  # Опросить конкретный OID на коммутаторе (SNMPv2c с паролем public)
  snmpget -v2c -c public 192.168.1.1 1.3.6.1.2.1.1.5.0

  # Выгрузить целую ветку параметров (например, список всех интерфейсов устройства)
  snmpwalk -v2c -c public 192.168.1.1 1.3.6.1.2.1.2.2.1.2
  ```
* **Золотой стандарт мониторинга (Четыре золотых сигнала Google SRE):**
  1. **Latency** (Задержка ответа сервиса).
  2. **Traffic** (Объем трафика / запросов в секунду).
  3. **Errors** (Процент ошибок, например HTTP 5xx или битых пакетов на порту).
  4. **Saturation** (Насыщение ресурсов — насколько близки к пределу CPU, RAM, диск или полоса канала).

## Частые вопросы на собеседовании
* **В чем разница между SNMP Polling (опросом) и SNMP Trap?** При Polling сервер сам по расписанию (например, раз в минуту) спрашивает устройство о его состоянии по `UDP 161`. При SNMP Trap устройство само мгновенно отправляет пакет об аварии на `UDP 162` сервера, не дожидаясь следующего опроса.
* **Почему для SNMP Trap и Syslog по умолчанию используется протокол UDP?** Чтобы в момент тяжелой аварии или перегрузки сети устройство не тратило ресурсы на установку TCP-сессий и бесконечные повторные отправки, а просто «выстрелило» сообщение о сбое. (В критичных системах для надежности используют Syslog поверх TCP/TLS).
* **Что такое Exporter в экосистеме Prometheus?** Небольшая программа-переводчик, которая устанавливается на сервер (например, `node_exporter` для метрик Linux или `snmp_exporter` для сетевых устройств) и отдает его показатели по HTTP в текстовом формате, понятном для Prometheus.
